# 로컬 LLM 서버

외장 GPU가 없는 미니PC 한 대에서 35B MoE 모델을 서빙하고, 홈랩 쿠버네티스의 AI 에이전트(kagent)가 이 서버를 모델 백엔드로 씁니다. 이 문서는 구성, 측정 결과, 운영 중 찾은 문제를 정리합니다. 과정 전체는 블로그 연재 1~4부에 있습니다. 전체 구성은 [README](../README.md)에 있습니다.

## 하드웨어와 통합 메모리

| 항목 | 값 |
|---|---|
| 본체 | GMKtec K8 Plus 미니PC |
| CPU | AMD Ryzen 7 8845HS (8코어 16스레드) |
| GPU | Radeon 780M 내장 GPU |
| 메모리 | DDR5-5600 32GB × 2 (듀얼 채널, 64GB) |
| 디스크 | NVMe SSD 2TB |
| OS | Ubuntu 26.04 LTS |

내장 GPU는 전용 메모리가 거의 없습니다. BIOS에서 GPU 전용 영역은 최소(1GB)로 두고, 커널이 시스템 메모리를 GPU에 빌려주는 영역(GTT)을 48GB까지 열었습니다. 모델 가중치와 KV 캐시는 이 영역에 올라갑니다.

이 구성의 상한은 메모리 대역폭입니다. 듀얼 채널 DDR5-5600의 이론 대역폭은 89.6GB/s이고, 데이터센터 GPU의 HBM은 수천 GB/s입니다. 토큰을 하나 생성할 때마다 활성 가중치를 메모리에서 읽어야 하므로 생성 속도는 대역폭이 정합니다. 그래서 MoE 모델을 골랐습니다. Qwen3.6-35B-A3B는 전체 35B 중 토큰마다 약 3B만 활성화하므로, 토큰당 읽는 양이 작아 이 대역폭으로도 쓸 만한 속도가 나옵니다.

## 서빙 구성

| 항목 | 값 |
|---|---|
| 서버 | Ollama 0.34.1 (컨테이너) |
| 백엔드 | Vulkan (Mesa RADV). ROCm과 비교한 뒤 Vulkan으로 정했습니다 |
| 모델 | Qwen3.6-35B-A3B, Q4_K_M 양자화 |
| 컨텍스트 상한 | 262,144 토큰 |
| 적재 | 한 번 올린 모델은 내리지 않고(`KEEP_ALIVE=-1`), 부팅 때 자동으로 올리는 systemd 서비스를 둡니다 |

`KEEP_ALIVE=-1`은 "올라간 모델을 내리지 않는다"는 뜻이지 "부팅 때 올린다"는 뜻이 아닙니다. 재부팅 뒤 첫 요청이 올 때까지 모델이 비어 있던 일을 겪고 나서 부팅 시 적재 서비스를 따로 만들었습니다.

### 동시 처리는 요청 하나

이 모델 계열은 Ollama의 병렬 처리 차단 목록에 들어 있어서, 병렬 설정을 넣어도 한 번에 요청 하나만 처리합니다. 프롬프트 캐시도 처리 슬롯에 남아 있는 KV만 살아남습니다. 그래서 대화 중간에 다른 요청이 하나라도 끼어들면, 다음 턴은 프롬프트를 처음부터 다시 처리합니다. 19토큰짜리 요청 하나가 6만 토큰 대화의 캐시를 밀어내 다음 턴이 4분 27초 늘어난 것을 측정했습니다(2026-09-03).

이 때문에 성능을 재려고 주기적으로 보내던 probe 요청을 없앴습니다. 감시가 실사용 대화를 망가뜨리는 구조였기 때문입니다. 지금은 실제 트래픽의 처리 로그에서 속도를 읽습니다.

## 측정 원칙과 결과

"느리다"를 구간별 숫자로 바꾸는 것부터 했습니다. 모델 적재, 입력 처리(prefill), 토큰 생성(decode)을 따로 재고, 입력 길이를 바꿔 가며 반복했습니다. 아래는 2026-09 측정값입니다(단위 tok/s).

| 구간 | 입력 4.8k | 입력 28.5k | 입력 118k |
|---|---|---|---|
| 입력 처리, GPU | 351 | 235 | 85 |
| 입력 처리, CPU만 | 105 | 74 | 측정 안 함 |
| 생성, 다중 토큰 예측(MTP) 켬 | 39.4 | 27.4 | 14.3 |
| 생성, MTP 끔 | 28.4 | 22.5 | 측정 안 함 |

측정으로 정한 설정은 다음과 같습니다.

- 입력 처리는 GPU가 CPU보다 3.2~3.3배 빨랐습니다. 입력이 길어지면 속도가 크게 떨어지므로, 짧은 입력으로 잰 값을 긴 입력에 그대로 적용하면 안 됩니다.
- 배치 크기(`num_batch`)는 512가 긴 입력에서 가장 좋았습니다. 128과 256은 느렸고, 1024는 차이가 오차 범위였습니다.
- IOMMU를 끄면 입력 처리가 4.2%, 생성이 1.8% 빨라졌습니다.
- 다중 토큰 예측(MTP)을 켜면 생성이 22~39% 빨라졌습니다. 대역폭 한계 안에서 한 번 읽을 때 토큰을 더 뽑는 방식이라 효과가 컸습니다.
- 배치 2048에 4만 6천 토큰 입력을 넣으면 GPU 작업 한 번이 약 2.3초 걸려, 드라이버의 GPU 멈춤 판정 한도(기본 2초)를 넘겼습니다. 한도를 10초로 올려 해결했습니다. 컨텍스트 상한과 배치 크기는 이 한도와 함께 계산해야 하는 값입니다.

## 관측

이 서버의 메트릭과 로그는 서버 위의 Grafana Alloy가 관측 hub로 보냅니다. 호스트 지표와 함께 GPU 사용률, GPU가 빌려 쓰는 메모리(GTT) 사용량, Ollama의 모델 적재 상태와 설정값을 수집합니다. 주요 알람은 다음과 같습니다.

| 알람 | 잡는 것 |
|---|---|
| OllamaAPIDown, OllamaModelUnloaded | 서버나 모델이 내려간 상태 |
| OllamaCPUFallback, OllamaCPUFallbackByGTT | GPU 대신 CPU로 돌기 시작한 상태 |
| OllamaConfigDrift | 컨텍스트 상한 같은 서버 설정이 바뀐 경우 |
| OllamaContextNearLimit | 대화가 컨텍스트 상한에 가까워진 경우 |
| ApuGTTHigh, ApuHighTemp | GPU 메모리 압박, 온도 |
| ApuPushSilent | 이 서버에서 관측 데이터가 끊긴 경우 |

설정 드리프트 알람이 실제로 잡은 일이 있습니다. 에이전트 쪽 모델 설정에 컨텍스트 크기를 적었더니 Ollama가 모델을 그 크기로 다시 올려 서버 설정이 바뀌었고, 알람이 바로 울렸습니다(2026-09-03). 그 뒤로 에이전트의 모델 설정에는 컨텍스트 크기를 넣지 않습니다. 관측 구조 전체는 [observability.md](observability.md)에 있습니다.

## kagent 연동과 프롬프트 캐시 문제

홈랩 클러스터의 kagent 에이전트 하나가 이 서버의 Qwen을 모델로 씁니다. 처음에는 응답이 지나치게 느렸습니다. 같은 질문 6개를 처리하는 데 38분이 걸렸고, 모델 호출 19번이 모두 캐시를 쓰지 못하고 프롬프트를 처음부터 다시 처리했습니다. 같은 질문을 kagent의 Python 런타임으로 돌리면 입력 처리 시간이 1,453초에서 260초로 줄고 캐시 재사용이 약 64%였습니다. 문제는 Go 런타임 쪽에 있었습니다.

원인은 Go 맵의 순회 순서였습니다. Go 언어 명세는 맵을 순회하는 순서를 보장하지 않습니다. kagent의 Go 런타임은 툴 정의의 속성과 대화 이력 속 툴 호출 인자를 맵에서 꺼내 요청을 만들었기 때문에, 요청마다 순서가 바뀌었습니다. 프롬프트의 앞부분이 매번 달라지면 서버는 같은 앞부분을 재사용하는 캐시(prefix cache)를 쓸 수 없습니다. Go, Ollama, 모델이 각자 명세대로 동작했는데 그 조합에서 캐시가 깨진 경우였습니다.

두 곳을 정렬하는 수정을 upstream에 냈고 둘 다 머지됐습니다.

| PR | 내용 | 머지 |
|---|---|---|
| [kagent #2693](https://github.com/kagent-dev/kagent/pull/2693) | 툴 정의 속성 순서 고정 | 2026-09-08 |
| [kagent #2988](https://github.com/kagent-dev/kagent/pull/2988) | 이력 속 툴 호출 인자 순서 고정 | 2026-09-28 |

kagent 1.0 알파를 일회용 클러스터에 올려 같은 조건으로 비교했습니다. 질문 처리 중 호출에서 다시 읽는 양이 새로 붙은 양의 몇 배인지를 보면, 수정 없음 8.7배, #2693만 4.4배, 둘 다 넣으면 1.0배였습니다. 1.0배는 새로 붙은 부분만 읽는다는 뜻입니다.

## 남은 과제

새 질문이 들어오는 순간에는 아직 캐시가 끊깁니다. Qwen의 대화 템플릿이 모델의 생각 과정(thinking)을 마지막 질문 뒤의 답에만 그리기 때문에, 새 질문이 오면 이전 답의 생각 부분이 빠져 앞부분이 달라집니다. 생각을 끄면 이 끊김은 사라지지만, 세 번 시험해 세 번 모두 에이전트의 툴 입력 품질이 나빠져서 해법으로 쓰지 않았습니다. 이전 생각을 보존하는 렌더링(`preserve_thinking`)을 Ollama가 지원하면 재측정할 계획입니다. 관련 변경은 Ollama upstream에서 검토 중입니다([#17121](https://github.com/ollama/ollama/pull/17121), [#18358](https://github.com/ollama/ollama/pull/18358)).
